## 2. What `sync/itad.go` already implements (217 lines, complete)

- Reads `itad.api_key` from `app_config`; if unset it returns "not configured" rather than failing the sync — contract-compliant.
- **Step 1, ID resolution:** `GET /games/lookup/v1?key=…&appid=…` per wishlist entry that has a Steam App ID but no cached `ITADId`, paced by a 500ms ticker (~2 req/sec), caching the result via `SetWishlistITADId`.
- **Step 2/3, prices:** `POST /games/overview/v2?key=…&country=US` in chunks of 200 IDs, then per entry writes:
  `p.Current.Price.Amount` → `best_current_price`, **`p.Current.Shop.Name` → `best_current_store`**,
  and the `Lowest.*` pair to the historical-low fields — plus `UpdateWishlistPricing`, per-entry error accumulation, and a progress callback.
- So the *real storefront name* path already exists and lands exactly where `price-sources.md` requires. Note it writes `best_current_store` but **not** `best_price_url` — GG.deals does set that from its `url` field, so ITAD is behind there.

## 3. ITAD access terms and limits (from `https://docs.isthereanydeal.com/`, read today)

- **Key:** register an app; keys and OAuth credentials are then generated. No payment mentioned anywhere in the access section. **Private personal use is explicitly allowed**; commercial use requires the app to be public. Nisaba is single-user and personal, so it qualifies.
- **Approval:** "For some endpoints you might need explicit approval for use." The docs do not state that `/games/lookup/v1` or `/games/overview/v2` require it — unverified either way; a 401/403 on first use is the signal to contact them.
- **Rate limit:** window-based. The docs state **1000 requests per 5-minute window** with a verified email, and warn that unverified accounts are being moved to lower limits. **Bobby's app setup page reports 100 per 5 minutes for this key**, which is authoritative for his account; both numbers are recorded. 429 with `Retry-After`; caching explicitly expected. No limit is exposed in response headers (`HTTP/2 200` plus `x-frame-options` only), so the setup page is the only place to read it.
- **Our pacing — wrong as written, corrected the same day.** The existing 500ms ticker is ~600 requests per 5 minutes: inside 1000, but **6× over a 100/5-minute budget**, so it would start collecting 429s. A per-entry first sync at a compliant 3s spacing would take ~33 minutes for 667 entries. See the second addendum — the batch lookup endpoint makes this moot, and `GG-002` is specified to use it.
- **Terms that bind implementation:** data must not be altered, and **affiliate tags on provided URLs must not be stripped** — so with ITAD the deal URL should come from ITAD's response, not be constructed.
- Live ITAD response **not observed**: no key is configured, so the `shop.name` parsing in `itad.go` is unverified against a real payload. Only the documented shape supports it.

## 4. Does GG.deals offer per-store data?

Two live calls to the endpoint Nisaba actually uses
(`/v1/prices/by-steam-app-id/?key=…&ids=…&region=us`), same request the app makes:

```
{"success":true,"data":{"292030":{"title":"The Witcher 3: Wild Hunt",
 "url":"https://gg.deals/game/the-witcher-3-wild-hunt/",
 "prices":{"currentRetail":"39.99","currentKeyshops":"24.49",
           "historicalRetail":"3.99","historicalKeyshops":"4.25","currency":"USD"}}}}
```

Response surface measured: game keys `["title","url","prices"]`; prices keys
`["currentRetail","currentKeyshops","historicalRetail","historicalKeyshops","currency"]`.

There is **no per-shop field anywhere in it**, which is why `applyGGDealsPrice`
can only ever write `gg.deals/retail` or `gg.deals/keyshop` — it is not a parsing
oversight, the data is not in the response.

Their API documentation could **not be verified from here**: `https://gg.deals/api/`
returns 403 to a non-browser fetch and web search returned nothing. So I can say
the endpoint in use has no per-store data; I **cannot** claim no other GG.deals
endpoint exists — I found no way to check. The CLAUDE.md:169 candidate list
("a different GG.deals endpoint") remains unverified in both directions.

## Recommendation

**Adopt ITAD as the pricing provider and leave the GG.deals code in place, unused.**

Basis: ITAD returns `shop.name` — the actual storefront — which is precisely what
`price-sources.md` requires and what GG.deals' endpoint structurally cannot
provide. The provider code, the settings entry, and the config key plumbing all
already exist, so the work is configuration plus one gap, not a new integration.

Cost: register an ITAD app and store the key (a manual step for Bobby); ~6 minutes
for the first full ID-resolution pass; add `best_price_url` handling to `itad.go`
so the deal link survives the switch; map ITAD's shop names in `storeShortLabel`
(`GG-003`); then execute the scorched-earth ruling on pre-cutover category rows
(`GG-002`).

Explicitly **not** recommended: switching to a different GG.deals endpoint (none
verified to have per-shop data, docs unreachable) or scraping gg.deals game pages
(brittle, no contract support, and their ToS was not verifiable from here).

What this does not fix: entries with no Steam App ID get no price from either
provider, since both key off Steam; ITAD prices are only for shops ITAD tracks;
and this reverses the 2026-06-28 note that "only GG.deals API is configured", so
the GG.deals sync path should be retired deliberately rather than left to drift.

## Addendum — 2026-09-16, live verification with a registered key

Bobby registered an ITAD app the same day and the key was used for read-only calls,
which closes the one claim §3 had to leave unverified (the parsing in `itad.go`
against a real payload):

```
GET /games/lookup/v1?appid=292030      -> found: true
                                          game keys: id, slug, title, type, mature, assets
                                          game.id: a UUID
POST /games/overview/v2  [<that id>]   -> top keys: prices, bundles
                                          prices[0].current.shop.name  = "Humble Store"
                                          prices[0].lowest.shop.name   = "GOG"
                                          prices[0].lowest.price.amount = 3.99 USD
```

What that settles:

- `p.Current.Shop.Name` and `p.Lowest.Shop.Name` in `sync/itad.go` are correct — a
  real storefront name reaches `best_current_store`. The contract gap is closable
  with the code that already exists.
- No explicit approval was needed for either endpoint: neither returned 401 or
  403, so §3's open "some endpoints need approval" question does not apply to the
  two in use.
- `current.url` **is present** in the payload and `itad.go` does not read it. That
  is the `best_price_url` gap named in §2, now confirmed fixable from data already
  being fetched — folded into `GG-002`'s outcome.
- Not used, but noted: `POST /games/prices/v3` returns a `deals[]` array of every
  shop offering the game with its price, so per-shop detail is available from ITAD
  if it is ever wanted. `overview/v2`'s current/lowest pair is enough for this
  round.
- Still unverified: whether `overview/v2` has a documented maximum batch size —
  the first real sync will show it.

## Addendum 2 — 2026-09-16, the rate limit is lower than the docs say, and there is a batch lookup

Bobby reported that his ITAD app setup page shows **100 requests per 5 minutes**,
not the 1000 the docs describe. That invalidated the pacing analysis above, so I
went back to their OpenAPI specification (`https://docs.isthereanydeal.com/openapi.json`,
263,165 bytes, 48 paths) rather than guessing, and probed with the live key:

```
POST /lookup/id/shop/61/v1   body ["app/292030","app/1091500","app/999999999"]
  -> {"app/292030":"018d937f-1212-7232-b23f-a046f6fd4a57",
      "app/1091500":"018d937f-2997-7131-b8b9-7c8af4825fa8",
      "app/999999999":null}
GET  /games/lookup/v1?appid=292030  -> the same id (018d937f-1212-…), confirming parity

GET /service/shops/v1  -> 34 active shops, {id, title, deals, games, update}:
  Steam=61, Humble Store=37, GOG, Fanatical, Epic Game Store, Blizzard, EA Store, …
```

What that means:

- **The rate limit stops being a design constraint.** `POST /lookup/id/shop/{shopId}/v1`
  resolves ITAD IDs in bulk — 667 wishlist entries become a few requests instead of
  667. The body is an array of the shop's own ids, **prefixed** (`"app/292030"` for
  Steam — the spec's example is `["app/220"]`), and unknown ids come back `null`.
- Shop ids are **numeric** (`{shopId}` = 61 for Steam), not the slug `steam`.
- `service/shops/v1` is the authoritative label source for `GG-003` — real storefront
  titles with ids, 34 shops actively tracked. That also answers the concern that
  GG.deals represented more stores: 34 is the honest count on this side.
- Path shapes cost two wasted requests to find: `POST /games/lookup/v1` → 405,
  `/games/ids/v1` → 404, and `steam` as a path param → 404. The OpenAPI spec is the
  cheap source for these, not probing.
- Still unverified: the exact semantics of `POST /lookup/shop/{shopId}/id/v1`
  (the reverse mapping) and whether a request batch has a size cap. Neither is
  needed for this round.
